# 通常操舵を基準に外乱区間とPP復帰区間を分ける収集

収集・WSL検証完了。停止地点＋追加10地点の左右22復帰イベント、正常完周10周から
1,999教師サンプル（学習1,441／検証558）を確保した。詳細は末尾の確定結果を参照。

前回の加算方式では、外乱中にもPPが逆操舵していた。新しい収集専用
`nominal_guide_then_pp_v1` は、実測通常周回の進捗に対応する操舵を基準にする。
推論入力やモデル、実行時のE2E制御は変更しない。

- ROS入力操舵の外乱は左右0.1 rad。0.25 s立ち上げ、1 s保持、0.25 s解除。
- 基準操舵も同じ割合で通常操舵へ移し、解除時に現在のPPへ戻す。
  コーナーでも開始時の操舵を固定せず、現在のコース進捗で補間する。
- 収集目標への到達による解除は開始1.25 s以降。横25 cm、向き4度、速度、
  進捗、壁時計の上限と独立した停止領域監視は先に適用する。
- 解除のブレンド全体を`hold`として除外し、純粋なPPへ戻った送信境界+150 ms
  以後の実測未来0.1～3 sのみを教師候補にする。新方式の制御メタデータも検証する。
- 従来方式は既定値として維持する。旧収集の保留状態・記録・予算を変更しない。

新しい有限計画はS00単独の左右2周を先行し、その結果を確認してから既存の
seed=915110で選んだ追加10地点の左右へ進む。最大10周・22イベント、各周1～3イベント。
S00の狙いは教師経路進捗119～120 mに横ずれと復帰が重なること。
外乱開始点と最大横ずれの位置を別々に報告する。通常RVizには発生位置のマーカーを出す。
実行前に通常2周の操舵・観測・実行環境をハッシュで照合する。

判定は実送信の操舵と通常操舵との差、実測操舵、横ずれ、向き、解除理由、
PP復帰確認、完周・通常停止、bag/センサ/教師の検証を分けて行う。
境界による短縮を「1秒保持成功」に数えず、失敗データも保全する。
同じ停止地点を試験のために危険な旧停止位置へ直接移動する操作は行わない。

実行コマンド（Windows編集・コミット後、同一コミットのWSL同期先）:

```sh
tools/with_wsl_training_lock.sh env PYTHONPATH=src .venv/bin/python -m pytest -q
```

基準操舵は通常周回の`issued_angle_rad`（最終制限後のROS入力）から作成する。
通常PPの入力許容値0.640001 radと、最終送信の上限0.5 rad・0.8 rad/sを区別する。
通常走行・復帰中にPPの元指令が0.5 radを超えても、既存の最終制限を適用する。
ガイドは[N,2]（進捗m、送信操舵rad）、有限値・単調性・最大0.25 mの間隔を検査する。

`pulse.effective_rad`は同じ直前指令を使った1ステップの反実仮想差であり、持続時間の
証明には使わない。保持判定では、実際に送信した操舵−同じ進捗の通常操舵が
符号付きで0.09 rad以上、ガイド選択率100%の区間が連続する時間を測る。
目標1 sに対し、20 Hz送信の時刻離散化を考慮した判定下限は事前に0.95 sとした。
実測車輪操舵と車体姿勢も別々に保存する。

運用は`tmp/time_recovery_separated_20260915/`のスクリプトをWindowsから実行する。
新規ルートの準備後、`install_plan.py`で実測通常周回とハッシュを検証した計画を配備。
`manage.py collect --pair 1`、`assess_pair.py 1`の順にS00左右を収集・転送・教師化して、
条件が通った場合にだけ`continue_after_pilot.py`で残り4ペアを実行する。
各周は公式1周終了まで走行し、上限1800 s、正常停止・bag閉鎖を確認する。
2周ごとに元データをWSLへ転送し、全ファイル・ディレクトリ構造・SQLite検証後に
その転送済み原本だけをAWSIMホストから片付ける。

実装コミットは`52891011a2a311cf52303b33baaca5e6d666e292`。
同一コミットのWSL全体テストは2588 passed / 4 skipped / 74 warnings。
スキップは従来の任意依存・公式パッケージ不足で、新規の16テストはすべて通過。
公式ROSイメージで通常RViz用MarkerArrayの遅延購読を確認し、実走画面でもS00左右を確認した。

S00の左右パイロットは各279.02 sで1周を完了し、正常停止・bag閉鎖・実行faultなし。
保持は左1.050 s、右1.040 s。停止区間119～120 mの横ずれは左11.06 cm、右10.05 cm、
復帰区間全体の最大は左11.89 cm、右10.97 cm（進捗約120.6 m）。
4度の向き解除条件を適用し、解除後も含む実測最大は4.42 / 4.34度だった。
WSLのセンサ・因果履歴・未来実測・準備済みtensorを検証し、左92 / 右89サンプルを採用。
保持中・解除中を教師にはしていない。S00左右を確認した後で追加10地点の収集へ進んだ。

計画の説明用`stop_site.map_xy_m`だけに旧116 m候補の座標が残っていたため、
`plan_map_annotation_erratum.json`に117 m候補の正しい座標を保存した。
実行条件の`start_s_m=117`、実送信位置のRVizマーカー、実測教師には影響しない。
旧方式との波形図は開始位置が116 / 117 mと異なることを明示している。
これらは教師走行の結果であり、再学習後のモデル性能は別途評価する。

保持時間の集計では、同じ`/clock`時刻で7.30159 ms間隔に送信された2指令を
途切れと誤判定する不具合を修正した。R09右の0.749999983 sという旧集計は、
修正後1.039999976 sとなった。旧レポートも`before_duplicate_clock_fix_*`として保全した。
追加の純粋関数は時刻が等しい指令を0秒の追加時間として扱い、送信順序の欠落や
両時計の150 ms超の間隔は継続の根拠にしない。最後の指令の継続時間を外挿しない。
集計修正のコミットは`1d209982b2bc40f0da9e74b2e24d4b7c4fbf87b8`で、WSL全体テストは
2600 passed / 4 skipped / 74 warnings。実走制御は5289101のまま固定し、原本・教師は変更していない。

1秒保持の厳格判定と教師としての採用は分ける。例えばR03右の送信時刻に155 msの
間隔があり、事前の150 ms条件を5 ms超えたため、連続して証明できる保持は0.67 s扱い。
R10左は0.949999979 sで、事前の0.95 s下限より21 ns短い。いずれも判定下限を変えず、
復帰確認・センサ履歴・実測未来が成立する教師だけを別に採用する。
最終的な全イベントの分類は`hold_evidence_detail.json`に保存する。

9回目のR07左は外乱前の進捗144.33 mで停止した。センサ鮮度の`STALE_steering`により
1回だけ再計算し、最終回の処理は28.81 msだったが、判断全体104.34 msが既存の80 msを
超えたため`COLLECTION_COMPUTATION_TIMEOUT`を検出した。外乱0件、停止確認済み、
bag閉鎖・各子プロセス終了・cleanupエラーなし。外乱やモデルの復帰失敗とは分ける。
CPU競合の寄与はこのログから断定しない。

この原本を失敗記録としてWSLへ転送・全構造とSHA/SQLiteを検証し、教師から除外した。
`replacement_amendment.json`でR07左の代替を1回だけ追加し、最大試行11回・正常完周10回・
外乱22件に変更した。元の10回予算、選定計画、失敗run IDは保持する。
代替IDは`codex-time-recovery-separated-g05-left-r1`、元の左と同じ参照・seed・splitを用いる。
`effective_data_plan.json`は教師用のrun ID対応だけを変更し、元の選定SHAも保全する。
実走コード・監視の閾値は変更せず、さらに失敗した場合の自動追加は行わない。
再開コマンドは`preserve_and_replace.py`（保全と1回限りの計画変更）、
`continue_final_pair.py`（残り左右の収集・WSL検証）の順。どちらも同じ対象へ二重実行しない。

## 確定した収集結果

graneple@192.168.3.10 のAWSIMで、過去のE2E試験の停止地点S00＋追加10地点の左右、計22復帰イベントを収集した。
正常完周は10周。外乱前の計算期限超過1回を含め、総試行は11回で終了し、追加の自動試行はない。

原本は失敗1回を含め11回分すべてWSLへ移送し、SHA-256・全ファイルとディレクトリ構造・
SQLite整合性を確認した。教師用10周はセンサ形式・時刻逆転・因果履歴・未来実測を検証し、
準備済み入力と元の観測からの入力再現一致も確認した。教師shapeは[N,30,2]、0.1 s間隔・3 s先まで。
実行用594ファイルは5289101と一致し、元のリモートcheckoutのHEAD/作業状態も維持した。
この収集用コンテナはすべて終了し、AWSIM側の検証済み転送元だけを片付けた。
