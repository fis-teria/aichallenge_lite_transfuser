# 大きな横ずれからのAWSIM実走収集

**1周3回の収集は左右とも全地点で成立し、5回への増量も実走した。5回条件は
時計更新の連続性が途切れ、2地点目の終了判定で中断したため、成立済みの上限は3回。**
実走先は `graneple@192.168.3.10`、教師検証はnative WSL。
全8試行を終了し、7周完走・1試行監視停止。全rawをWSLへ転送・検証し、
採用できた13復帰イベントから1,094件のCameraアンカーと実測未来教師を準備した。
学習用812件、検証用282件。今回モデルの再学習・E2E性能評価は実施していない。

3回条件はP00（復帰60m）、S00（停止地点手前118m）、P02（245m）。
5回条件では160m、285mの2地点を追加した。開始地点間の40m間隔を維持し、
横ずれ量は左右20cmのまま。比較のためこの試行群では地点を固定した。
ユーザー指示の「最初3回、以後+2」に従い、左右3回の教師検証後に5回を開始した。
初期6試行の上限は校正後8試行に変更し、最後の追加再収集もその枠内で実施した。
7回は未実走。既存の両側20cm地図通過候補だけでは、40m間隔を維持して
停止地点を含む7地点を組めない。40/60cmの実走データも今回の収集には含まれない。

## 5回条件の中断原因と残る作業

S00の終了直前に、隣接publicationのsim時刻が約170ms進んだ。実際のpublication間の
wall時間は58.81msであり、170ms間操舵指令が送られなかったことを意味しない。
連続性の150ms条件で安定時間がリセットされ、10秒の復帰窓の終端までに1秒を
再確認できず、`RECOVERY_NOT_STABLE_AT_END`になった。
終了時は横ずれ1.684cm、向き-0.196度、速度1.288m/sで、これらの値自体は範囲内。
停止領域監視・車体の曲がり不足による中断とは区別する。

このrunのS00教師は採用せず、続く3地点の外乱を抑止した。1周後の停止とbag閉鎖は正常。
右3回の再試行成功も、この時計更新問題の恒久的解消を示すものではない。
次の5回再試行の前に、経路メッセージ受信・ROS callback・clock更新の遅延を切り分ける。
3回から5回で準備経路は1,223点から1,945点へ増えており、受信負荷は確認候補だが、
現時点では遅延元を断定していない。判定幅や停止監視を緩めて採用を増やす変更はしていない。
[WSLでの原因再確認](evidence/time_large_recovery_live_20260915/five_event_end_stability_native.json)に
元controlのSHA、隣接publication、安定時間リセットを記録した。

## 実行条件と校正履歴

目標5km/h、操舵・センサ・停止領域・計算期限の監視は既存条件を維持する。
復帰確認後の未来3秒と次回の安定条件を満たすまで、次の横移動を開始しない。
回数の判定は予定数、準備開始数、実測目標到達数、復帰成功数、有効教師数を分ける。
停止や目標未達・未復帰・スキップがあれば5回へ増やさない。

専用実行先は `/home/graneple/e2e_autonomous/time_recovery_large_live_20260915`。
完成済みの小外乱・合成試験の実行先を再利用しない。
1周+未来確保後に停止、1試行の上限30分、bag上限2GiB、空き10GiB以上を維持する。
最大2runごと、容量に応じて1runごとにnative WSLへ転送し、hash・構造・SQLiteを
検証してから転送済みの新規rawだけを限定削除する。

実行したコマンドの例（専用配備・SHA検証後。既存run IDを再利用しない）:

```sh
PYTHONPATH=/home/graneple/e2e_autonomous/time_recovery_large_live_20260915/source/src \
python3 /home/graneple/e2e_autonomous/time_recovery_large_live_20260915/source/tools/run_time_recovery_awsim.py \
  --campaign-root /home/graneple/e2e_autonomous/time_recovery_large_live_20260915 \
  --run-id codex-time-recovery-large-live-g03-left-r01 --side left \
  --speed-policy aligned_gain4_v1 --separate-cpus
```

通常のRVizに基準経路、準備経路、実走履歴、外乱開始マーカーを表示する。
Camera/LiDAR/egoを連続保存し、確認済みの通常PP復帰区間だけを教師候補にする。
再学習は今回の範囲外。

初回左20cmのP00は準備操舵172回、最大横ずれ26.97cm。復帰窓60～61mで
25.75～26.83cm程度となり、目標の15～25cmに収まらず`TARGET_NOT_REACHED`。
要求・通常PP復帰の確定はなく、以降のイベントは抑止された。この試行は教師採用しない。
修正は準備保持距離を2mから4mにし、同じ復帰位置までの整定時間を確保するもの。
横ずれ・向きの採用幅、停止監視、12秒の準備期限は変更しない。
停止地点手前S00では保持4mのために準備開始を早めると、準備経路が地図条件を
満たさなかった。S00は検査済みの保持2mを維持し、P00/P02だけ4mにする。

2回目の左周回ではP00が約24cmからの通常PP復帰に成功した。一方S00は横19.1cm時に
向き約-3.49度となり、同じ目標判定で未成立。S00の準備経路だけ元の教師指令経路を
ずらす方式へ変更して比較する。通常完走の追従誤差を再度指令する影響を切り分けるためで、
目標値・判定幅・監視を緩める変更ではない。

右側の同じS00条件は約-30cmまで振れ、目標未達後の120.34mで停止領域監視が作動した。
正常停止・bag閉鎖を確認して保全し、失敗runの教師採用は0件とする。
指令経路を修正した左3回目はP00・S00の2イベントに成功したが、P02の開始223～224mで
速度1.41～1.43m/sとなり、上限1.4m/sの開始条件でスキップされた。
2m後方へずらすだけでは速度の揺れが残るため、実測で233～247mの速度が
1.260～1.306m/sだった範囲を選び、P02は準備開始235m・復帰245m、保持2mとした。
新しいP02の準備経路と候補復帰経路は左右とも地図検査を通過した。
5回の候補は元の3地点に160m・285mの2地点を追加する。開始地点間の40m間隔を維持する。

修正後の左 `g03-left-r04` は3イベント全成立、各94件、計282件の有効Camera教師を確認した。
右 `g03-right-r02` も3イベント全成立・完周したが、制御publicationのsim時刻に
155～170msの間隔が4か所あり、150msの連続性条件でその区間を無効にした。
その区間を未来3秒に含むアンカーも除外され、P00は53件・P02は67件の採用となった。
両地点とも実測15～25cm帯の採用アンカーは0件。Camera/LiDARのcapture時刻は連続しており、
カメラの最大間隔は約105ms、LiDARは約100ms、無効メッセージ・逆行は0だった。
走行成功と20cm帯の教師取得を同一視せず、この右runを増量の根拠には使わない。
有効な小横ずれの214アンカーは検証候補として保持する。

残り2試行の用途は、同じ右3回条件の再収集と、その検証が通った場合の左5回収集へ変更した。
最大8試行は増やさず、時刻・横ずれ・停止監視の条件も維持する。
右3回の再収集が成功しても、それだけで時刻の揺れ自体が解消したとは扱わない。
