MPPI-Generic：GPU並列化と制御周期を分けて測る

Bogdan Vlahov, Jason Gibson, Manan Gandhi, Evangelos A. Theodorou / Georgia Tech ACDS Lab

MPPIの候補数を増やせても、センサ観測から指令適用までに間に合うとは限りません。MPPI-GenericのCUDA実装を、候補探索の仕組み、CPUとGPUの処理分担、計時範囲から読みます。既存の参照空間MPPIとの違いを整理し、導入を判断するために必要な測定を具体化します。

確認日：2026-10-10。論文の限定節と固定版の著者コードを静的に確認しました。ライブラリのビルド、ベンチマーク追試、制御実装の変更、学習、AWSIM・実車走行は行っていません。

1. 課題：探索の量と、判断を返す期限

学習器の未来経路が障害物へ近づくとき、下流の制御側には、候補を比較して経路や操作を修正する役割があります。Information-Theoretic MPCはサンプリング制御の基礎、RMPPIは追従器を含む外乱への応答、BayesRaceは予測モデルの残差を扱います。今回は、その計算をどのように並列化し、何を計時するかに範囲を絞ります。

公式READMEの固定版はC++/CUDAライブラリとしてNVIDIA GPU、GCC/G++、Eigen、CMake等を挙げています。CUDA 10以降に対応し11.7以降を推奨する記述ですが、対象PCでの互換性を今回検証したわけではありません。CPUのPython処理を同じ関数名へ置き換えるだけで導入できる構成ではありません。

2. 仕組み：候補の時間発展と、候補間の並列化

公式アルゴリズム解説では、平均操作系列の周りに候補を作り、モデルで状態を展開してから重みを付けます。下の式は同じ共分散の加法Gaussian雑音を使う説明形です。Sには必要な操作コスト・重要度補正を含めます。雑音分布を変更した実装へ、補正を省いたまま移植する式ではありません。

Uⁱ = Ū + εⁱi番目の操作系列。候補数をKとし、εはここでは平均0のGaussian雑音。
ρ = mini Sⁱ
wⁱ = exp[−(Sⁱ − ρ)/λ] / Σj exp[−(Sʲ − ρ)/λ]		λ > 0。最小値を引いてから計算する。小さいλでは少数の候補へ重みが集中しやすい。
Ū ← Ū + Σi wⁱ εⁱ重み付き更新。有限候補から得た平均であり、大域最適性や衝突回避の証明ではない。

Vanilla MPPIのcomputeControlには、初期状態のGPU転送、rollout、コストのCPUへの転送と同期、CPUでのbaseline・normalizer計算があり、Gaussian samplerがGPUで重み付き平均を更新して結果を返します。「GPU実装」でも転送やCPU処理を無視できません。

原著v4の§III-Cは、状態展開とコスト評価を分けるsplit kernelと、一つへまとめるcombined kernelを比較します。前者は時間方向のコスト評価を並列化でき、後者は中間状態のglobal memoryへの書き出しを減らせます。固定版のchooseAppropriateKernelはshared memory容量を検査し、利用可能な両方式を計時して選びます。その選択は対象の設定に対する初期評価であり、全入力での最悪時間を保証するものではありません。

3. 条件付きの計算時間：候補数で優劣が変わる

原著v4の§V・Tables I/IIは、差動駆動モデルと目標・障害物コストを使い、刻み0.02 s、100段の予測で実装を比較します。換算した予測時間は2 sで、0.02 sは処理時間の実測値ではありません。AutoRally、MPPI-Generic、Nav2は各10,000回、TorchRLは1,000回。block寸法は比較間で共通で、機種ごとの最高性能まで調整した結果ではありません。

本記事の解釈として、比較したいのは「最も短い平均」だけではありません。同じモデル・コスト・探索範囲のまま候補数を増やせるのか、出力の質や期限超過がどう変わるのかも必要です。計算の改善だけでは、モデル誤差、古い地図、候補に回避経路が含まれない問題を解決できません。

5. 現行プロジェクトのMPPIは、探索するものが違う

以下は公開系統8f89a60の静的確認です。ReferenceMppiはNumPy/SciPyで参照経路の4係数を探索します。通常の横オフセット群は256候補×3反復で、成立しなければ曲率を積分する候補群を追加します。予測長は最大16 mの空間距離で、上の論文の100段×0.02 sとは同じ条件ではありません。

未知領域・車体余裕・形状を検査し、不成立候補を除き、重み付き平均の経路も再検査します。終端で元の経路へ戻ることはコスト項で、硬い終端制約ではありません。その後のPure Pursuitで操舵へ変換します。確認した静的占有のplannerは移動物体を予測しません。また、リポジトリ全体にCUDAコードがないという確認ではありません。

低速試験用設定のcontroller_wall_period_s=0.05は50 ms周期、plan_max_age_s=0.5は計画の鮮度条件です。設定値だけでは実際の適用周期や最悪時間を確認できません。既存rollout02記録の計算時間最大42.52 msは、5 km/h目標・静止箱1個・NPCなしの限定試験です。周回成功判定ではなく外部supervisorで終了し、複数配置の成功率や実車体最小距離は未測定です。元の箱回避の記事の条件を保ち、新しい実験結果として数えません。

6. 強み・限界と、導入判断の比較軸

再利用できるCUDA実装とモデル・コスト・サンプリングの分担は、探索を大きくする候補になります。一方、APIへ接続できること、低い平均計算時間、全候補が無効なときの処理、最終指令の安全性は別に確認する項目です。PSFの終端安全条件も、ライブラリを導入しただけでは得られません。

本プロジェクトでの比較案は二つです。まず既存の参照空間探索を同じ意味のまま高速化し、候補数・出力・無効判定をCPU版と比べる方法。次に操舵・加減速の操作系列を車両モデルで展開する方法です。後者は制御方式そのものの変更で、GPU移植と同じ評価に混ぜられません。現時点ではどちらも未実装です。On-Track SysIDなどのモデル同定、動的障害物の予測、データ生成の候補も引き続き別の比較軸として残ります。

7. 必要なデータ・計算資源・検証

以下は本記事の導入候補で、今回実施した操作ではありません。

  1. 境界を固定する：状態・操作の単位、車両モデル、刻み、座標、予測長、最終経路と指令の契約を決める。同じ入力と候補で、CPU/GPUのコスト・採用結果・不成立時の動作を比較する。
  2. 同期ログを用意する：センサ取得、入力確定、転送開始、GPU処理完了、返却、最終検査、指令適用の時刻を区別する。学習用と評価用をrun/scenario単位で分け、低速データから高速域の誤差を推定しない。
  3. 資源を一組で記録する：CPU/GPU、メモリ、OS、driver/CUDA、依存とcommit、block寸法、候補数K・予測長H・反復Iを保存する。推論・SLAM等とGPUを共有するときの混雑、温度・電力制限、転送と地図更新も測る。
  4. 返却までと適用までを分けて測る：固定seed、warm-up、同期方法、測定回数をそろえ、平均・p50・p95・p99・最大値・期限超過率を残す。処理段階ごとの時間に加え、観測から適用までの全体時間を測る。
  5. 失敗を別に評価する：全候補棄却、NaN、地図更新、計算期限超過、GPU異常、古い出力、平均経路の衝突を個別に扱う。最終検査と外部停止監視を保ち、停止時間、接触、車体最小距離、成功率を同じ条件で比較する。

学習データを増やす提案と、制御時の探索を増やす提案は必要な資源も異なります。歩行者を含むnavigationへ移す場合は、人の予測誤差や通行の相互作用を追加評価する必要があります。この記事の差動駆動ベンチマークや静止箱の記録から、対人安全や高速車両の能力は導けません。
