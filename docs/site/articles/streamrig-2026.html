PAPER / MULTI-CAMERA ODOMETRY

StreamRig：複数カメラの配置を生かし、移動を逐次推定する

同じ時刻の周囲画像をひとまとまりとして理解し、その小さな表現を時間方向につなぐ。StreamRigは、学習済み3Dモデルを固定したまま、校正済みの多眼カメラから移動量を推定する研究です。注目点はカメラの枚数だけでなく、カメラ間の既知の幾何・履歴の圧縮・基準時刻の更新を組み合わせた設計にあります。

01 / PROBLEM

「同時に見ている関係」と「時間をまたぐ関係」を両方使いたい

rigは、同じ台に固定され、同時刻の画像を取得するカメラの組です。各カメラの焦点距離などを表す内部パラメータと、カメラ同士の位置・向きを表す外部パラメータが分かれば、違う方向の画像を幾何的に関係づけられます。前方が一時的に見づらくても、側方の観測が移動推定を支える可能性があります。

一方、長い映像の全画像・全パッチを記憶すると、計算とメモリが増え続けます。単眼用のstreamingモデルへ同時刻の複数画像を順番に入力するだけでは、同時観測であることや既知のカメラ配置を十分に利用できません。StreamRigは、空間方向の理解を先に行い、時間方向へ渡す情報を小さくすることでこの問題に取り組みます。[1, §I–II]

02 / MECHANISM

3Dの理解を固定し、姿勢を読む部分だけを学習する

1. MapAnythingがrig全体を共同認識する

凍結したfront-endへ、画像、内部パラメータから求めた画素のray方向、基準カメラに対する外部パラメータを渡します。DINOv2由来の画像特徴へ幾何情報を組み込み、カメラ間のAttentionを使った特徴を生成します。校正情報を直接受け取るのはこのfront-endで、その後の学習部には外部パラメータを別入力しません。したがって校正を省いても同じ方法になるわけではありません。[1, §III-A]

2. Rig-Resamplerが姿勢推定に必要な特徴へ圧縮する

2層のcross-attentionと学習可能なqueryで、各カメラのパッチ特徴を16個のlatent tokenへまとめます。論文の224×224画像・5カメラの例では、1,280個のpatch tokenが80個になります。これは後段の時間方向の処理とcacheを小さくする工夫であり、画像encoder自体の計算がなくなるわけではありません。[1, §III-A]

3. CausalBridgeは現在と過去だけを参照する

8層のAttentionが、カメラの識別、anchorかqueryかという役割、基準カメラの印を使って圧縮特徴を処理します。同一rig内の参照は自由ですが、時間方向では未来を見せません。過去rigのkeyとvalueをcacheへ保存し、新しいrigが来たときに再利用します。公開実装にも逐次推論用のStreamCacheRunnerがあり、全窓の因果推論との等価性を調べるテストが用意されています。本記事ではそのテストを実行していません。[3]

特徴的なのがanchor snapshotです。基準rigのtokenをqueryごとにコピーし、そのコピーと現在rigを相互に参照させます。コピーはそのquery専用なので、基準側を更新するために未来の観測を混ぜる必要がありません。通常の固定anchorよりも、比較する2組の間で姿勢に関係する情報をやり取りできる設計です。[1, §III-B]

4. 出力は基準カメラから見た現在カメラの姿勢

Pose headは回転と並進を読み出し、現在rigの基準カメラの座標をanchorの基準カメラ座標へ変換するT(a←t)を出します。他カメラの姿勢は既知の校正から作れる補助的な学習目標です。車体中心の位置や地図の絶対座標がそのまま出るという契約ではないため、車両へ接続するときはカメラとbase_linkの関係を別途扱います。[1, §III-B]

5. Re-anchoringが記憶量を制限する

一定数Nのrigを処理したら最後のrigを次のanchorにし、ブロック間の推定を合成します。これで状態をブロック長に応じた範囲へ抑えます。短すぎるブロックでは合成回数が増え、長すぎると学習した移動範囲を超えます。NCLTの標準モデルではN=24付近の並進driftが小さく、学習上限を超えるN=64では悪化しています。[1, §III-D・IV-C]

古いrigのtokenをさらに減らすlong-history方式も検討されていますが、こちらの状態量は系列長とともに増えます。「圧縮したから永久に一定メモリ」ではなく、通常方式のメモリ上限を作るのはre-anchoringです。また、基準の更新は過去の地図へ戻って誤差を修正するloop closureとは異なります。

03 / TRAINING

相対姿勢だけで学習するが、良い初期値と対象rigのデータが重要

学習対象はRig-Resampler、CausalBridge、Pose headの合計74.6Mパラメータ。論文のシステム全体638Mの11.7%です。学習するパラメータが少なくても、推論時には固定した大きなfront-endも動作します。[1, §III-C]

  1. Stage I：画像群どうしの再位置推定で初期化。軌跡上から作った2つの画像群を使い、相対姿勢を学びます。多様な配置・移動を経験させ、固定特徴から幾何を読む能力を作ります。入力の校正へ回転1.5度・並進0.1 mのSE(3)ノイズを加え、教師は正しい姿勢のままにします。
  2. Stage II：対象rigの時系列へ適応。同じ学習部へ因果maskとanchor snapshotを適用し、rigの窓から姿勢を学びます。回転誤差と、正解の移動距離で正規化した並進誤差を使い、近距離の学習が遠距離の大きな誤差に埋もれにくくします。

ここでの「相対姿勢だけ」は、StreamRigの追加学習の教師を説明する表現です。正解poseが不要という意味でも、MapAnythingまでゼロから姿勢教師だけで学習したという意味でもありません。Stage IなしのNCLT ablationでは並進driftが2.77%から41.37%へ悪化しており、凍結モデルへランダムなheadを載せるだけでは同等になりません。[1, §III-C・Table III]

論文の代表設定と配布設定を分ける。論文では可変長窓[6,48]と576k窓の学習を説明しています。確認した公式YAMLではNCLTが[6,48]・57,600窓×10 epochs、KITTI-360が[3,12]・48,000窓×10 epochsです。再現時は対象データセットの設定を固定し、全データセットで同じ窓長・学習予算だったとは仮定しません。[4]

driftとATEは違うものを測る

  • t_rel：区間長に対する並進の相対誤差。NCLT・KITTI-360では100–800 m、TartanGround・ZJHでは10–80 mの区間で計算します。
  • r_rel：距離あたりの回転の相対誤差。この記事の単位は度 / 100 mです。公開コード内部の度 / mと取り違えないようにします。
  • ATE：軌跡全体を正解に合わせたあとの位置誤差。SE(3)は回転・並進で合わせ、Sim(3)はさらに1つの全体scaleを合わせます。走行距離や環境が異なる行のATEをそのまま順位づけることはできません。

再現上重要な、公開コードの集計と欠損処理

READMEの結果はstride 3、100–800 m区間、全系列ATEのSE(3)整列という条件です。ただし、論文本文の概略だけでは集計の細部を取りこぼします。公式commit 3a41caf249a484b71b20c562f79af6a5e44cbed1の評価スクリプトを読むと、次の区別があります。[2] [5]

  • NCLT：各日付の中では有効区間数で相対誤差を集計し、その後2日付を等重み平均します。ATEも日付ごとに求めて等重み平均します。時刻差が1,000 msを超える隙間では、前後の推定軌跡をGTの相対姿勢で接続します。
  • KITTI-360：4眼画像と公式poseのそろう連続したvalid runで推論します。0009の6本と0010の4本、合計10本です。t_rel / r_relは全runの有効区間数でpoolし、ATEはGTでrun間を接続したdrive全体で求め、2 driveのGT経路長で重み付けします。
  • 論文との記述粒度：本文はKITTI-360の指標を経路長で重み付けすると説明しますが、公開コードでは相対誤差は区間数によるpooling、ATEは経路長重み付き平均です。本記事は両者を同一の平均方式として省略しません。

GT接続は推定区間の内部形状を修正する処理ではありませんが、記録が欠けた区間の移動を正解で補います。その空白も含めた自律的な追跡・復帰能力は測れていません。また、NCLTの配布評価はN=24、KITTI-360はN=3が既定です。論文の表を比較するときは、同じ系列だけでなく、re-anchoring、サンプリング、scale、欠損処理を一緒に記録する必要があります。[5]

何に対して良くなったのか

著者の比較では、StreamRigは4データセットすべてで、GTを与えるoracleを除いた方式の中でt_relとr_relが最小です。NCLTではG2G-chainの6.08%・3.54度 / 100 mに対して2.77%・1.39度 / 100 m、KITTI-360では単眼CUT3Rの3.59%・1.63度 / 100 mに対して2.59%・0.98度 / 100 mです。[1, Table I]

比較相手には対象splitでfine-tuneした方式と公開重みをそのまま使う方式が混在し、入力カメラ数も同じではありません。さらにKITTI-360のATEでは、scale整列を含むSTream3Rが53.6 mで、StreamRigのSE(3)整列63.7 mより小さくなっています。したがって「すべての指標・すべてのVO / SLAMに勝つ」という結論にはしません。

05 / COMPUTE AND RELEASE

計算は小さい時間処理と、大きい固定front-endに分かれる

論文Table Vでは、RTX 4090、BF16、batch 1、入力をメモリへ載せた状態、512回の到着について、5×224×224画像からposeまでの中央値を26.2 ms / rig、throughputを38.2 rigs/s、peak allocated GPU memoryを2.6 GiBと報告します。内訳はfront-endとResamplerが24.9 ms、BridgeとPose headが約1.3 msです。[1, §IV-E]

この中央値は、センサ取得からROS配信までの遅延上限でも、TimePathと同時実行した実測でもありません。とくにFig. 1の精度はStreamRig N=24と9-frame版CUT3R、費用はStreamRig N=2とrecurrent版CUT3Rという別設定です。高精度側の設定に26.2 msを無条件で対応づけないようにします。

G2G-chainの50.9 msとの差も、毎回2つのrigを再encodeする実装を含む比較です。直前rigの特徴をcacheするpairwise方式は、N=2のStreamRigと同じ計算を行うため、そこでの主な利点は履歴を使った精度です。[1, §IV-E]

06 / LIMITS

強みを生かすには、何が壊れるかも確認する

  • 長距離drift：ブロック間の姿勢をつなぐ以上、誤差は残ります。再訪問検出の探索的な結果はありますが、loop triggerの定量評価や地図を使った共同最適化は将来課題です。完成したloop-closing SLAMとしては扱いません。
  • 学習範囲の外：anchorからの変位が学習範囲を超えると、出力変位が飽和する傾向があります。窓のframe数だけでなく、速度とstrideを含めた実際の移動距離が重要です。
  • rigへの依存：Stage Iの校正ノイズによる学習はありますが、新しい取付け誤差・時刻ずれ・片眼欠損を広範囲に許容できるという実証にはなりません。
  • 実運用の頑健性：雨、露光差、レンズ汚れ、rolling shutter、激しい遮蔽、長い停止、低速旋回に対する本車両での失敗率は不明です。論文に登場する多様な環境だけから安全な停止判断まで保証できません。
  • 信頼度と安全動作：poseを出せることと、そのposeを使ってよいか判定できることは別の設計課題です。制御へ入れるなら、異常値・遅延・不連続・外部参照との不一致を検出する条件が必要です。

最初の2項目は論文の実験・将来課題に基づきます。後半は本プロジェクトへ適用するときの検証課題であり、著者がそれらの条件で失敗したと報告した、という意味ではありません。[1, §IV-C・V]

07 / PROJECT CONNECTION

本プロジェクトでは、まず位置合わせの独立候補として考える

確認した公開mainのモデル・制御コードは、Camera RGB・2D LaserScan・ego stateの時系列から、観測時点のbase_linkで0.1–3.0秒後のXY 30点を予測するTimePathV1です。車速と実操舵角の局所オドメトリを使った位置合わせ、任意のCartographer・占有地図・局所MPPIという経路も記載されています。StreamRigが必要とする同期済み多眼rigの校正・データ契約は、この確認範囲では見つかっていません。[7]

このため、StreamRigは既存画像encoderの単純な置換ではなく、新しい観測・姿勢推定系の候補です。TimePathのwaypoint出力とも、2D LiDARから作る占有情報とも役割が違います。現在の構成はシステム構成とTimePathの入出力、地図の整合性とloop closureはCartographerの記事へつながります。

候補A：ログ上で比較する独立オドメトリ

最初の用途として考えやすいのは、制御へ入力せず、同期rigのログから推定した移動を既存の局所オドメトリや独立GTと比べることです。どの条件で車速・操舵からの推定と差が開くかを観察できます。ただし、比較対象を教師にも使った場合には独立した精度検証にならないので、GTの由来を区別します。

候補B：観測・保持経路の位置合わせを補助する

十分な検証後には、過去の観測や保持経路を現在座標へ変換する姿勢源の候補になります。採用するなら、どの時刻のどの座標変換を置き換えるかを限定します。特にStreamRigのanchor更新による内部基準変更を、そのまま外部のodomの飛びにしない接続が必要です。LiDARの占有判定、未知領域の扱い、独立した安全監視は別に維持します。

候補C：圧縮した時系列表現という設計を参考にする

rig特徴を圧縮して履歴へ渡す考え方は、センサ融合や長い履歴を扱うモデルの参考になります。ただし、本プロジェクトの4×4 camera tokenや2D scan tokenと、StreamRigの多眼幾何を学んだlatentは同じものではありません。現在のGRU履歴をCausalBridgeへ置き換える効果は別の仮説で、入力・教師・計算量をそろえた再学習が必要です。

08 / VALIDATION PLAN

導入判断を、再現・未見データ・実時間性に分ける

  1. 元の結果を再現できるか。公式commit、重みSHA-256、split、stride、N、GT gap接続、SE(3) / Sim(3)、集計方式を固定します。GTで接続した公表条件の再現と、接続なし・欠損ありの運用条件を別々に報告します。
  2. 座標・因果性の契約が正しいか。合成した既知の移動で変換の向きと尺度を確認し、未来画像の改変が過去出力を変えないこと、全窓とcache推論の一致、anchor更新前後の連続性を検査します。
  3. 対象rigの未見runで有効か。既存の局所オドメトリと同じGT・同じ有効時間で比較します。短区間の相対誤差、長距離drift、停止中の漂い、scale誤差、回転誤差、追跡失敗・再初期化率を分けます。
  4. 失敗を検出できるか。時刻ずれ、片眼欠損、校正ずれ、画像ぼけ、動く物体、暗所、長い停止・旋回を含む条件で、誤差だけでなく異常検出と出力停止までを測ります。
  5. 既存処理と共存できるか。TimePath・地図処理と同時に動かし、センサ時刻からpose利用までの中央値・p95・p99・最大遅延、GPU / host memory、queueの蓄積、温度による低速化を測ります。4090単体の中央値はこの測定の代わりになりません。
  6. 制御へ入れた結果が改善するか。上の条件を満たした後に、停止条件を備えた限定シミュレーション試験へ進みます。周回、接触、最小距離、停止、復帰を複数runで確認し、オフラインpose精度の改善とclosed-loopの改善を分けて判断します。

以上は記事として整理した検証案です。学習・実装・実車・AWSIMの試験を行った記録ではなく、未確認事項を確認済みへ変えるための判断基準です。
